# LedgerLine threat model and current gaps

This register records implemented controls and remaining risks as of 2026-11-08. It is not a security certification. LedgerLine is not ready for real-money use.

| Threat | Current controls | Remaining risk / required work |
|---|---|---|
| Password attacks | Public password validation; minimum 12 characters; BCrypt; 72 UTF-8-byte limit; generic login failure; password hashes excluded from API responses. | No rate limiting, progressive delay/lockout, MFA, password reset, email verification, breached-password detection, or credential-stuffing monitoring. |
| JWT tampering / invalid tokens | HS256 signed tokens; Base64 secret must decode to at least 32 bytes; required issuer, subject, expiry, and known-role claims; expiry and signature are validated; token TTL defaults to 15 minutes. | No asymmetric key separation, rotation/key ID support, audience validation, refresh-token flow, or denylist. Symmetric key compromise enables token forgery until rotated. |
| Privilege escalation | Public registration always assigns `ACCOUNT_HOLDER`; initial ADMIN creation is an explicit, environment-gated startup bootstrap (not an HTTP endpoint); later role changes require ADMIN and are audited; roles/status are reloaded from DB per request; unknown routes fail closed. | Bootstrap secrets must be set only for first provisioning and removed afterward; secrets/host protections and operational approval processes are not managed by the app. |
| Unauthorized account access | Account-holder reads/statements require OWNER/VIEW/TRANSFER permission; transfers require OWNER/TRANSFER on the source. Financial writes recheck permission after locking rows. ADMIN/AUDITOR broad reads are intentional. | MySQL locking behavior and permission revocation races still need testing on MySQL; do not expose account data outside these service checks. Admin access grants remain high-impact. |
| Auditor financial writes / history changes | AUDITOR has read-only account, statement and audit endpoints. Transfer and admin posting endpoints require ACCOUNT_HOLDER and ADMIN respectively. V1/V4 define ledger, audit, transaction and settlement append-only triggers. | DB administrators can alter triggers/schema. MySQL trigger execution, separate DB privileges, external tamper evidence and monitoring remain unverified/absent. |
| Session/token misuse | Stateless API; browser token stays in JS memory (not localStorage/sessionStorage); logout clears it; 15-minute default expiry; DB status checked per request. | A live token can be read/used by injected same-origin script. Logout does not revoke a copied bearer token, which remains valid until expiry. No refresh or revocation mechanism exists. |
| Public administrator registration | Public register DTO omits role and registration forces `ACCOUNT_HOLDER`; integration test submits an `ADMIN` field and confirms the stored/returned role is `ACCOUNT_HOLDER`. Initial ADMIN provisioning is a disabled-by-default, environment-gated startup bootstrap, not a public endpoint; subsequent role changes require an ADMIN and are audited. | Operators must enable the bootstrap only for initial provisioning, protect those environment values, and disable/clear its password immediately afterward. Deployment-level approval and secret management remain external responsibilities. |
| Credential exposure | DB password and JWT secret are required environment values; `.env.example` has placeholders only; passwords are BCrypt-hashed and never returned. | Real deployment secret manager, rotation, DB privilege separation for Flyway/runtime, environment/process access controls, and log/backup protection are not configured. Do not put secrets in frontend `VITE_*` variables. |
| CORS / cross-site requests | Allowed origins are explicitly configured; credentials are not enabled; API uses bearer authorization headers rather than ambient cookies; CSRF is disabled for this stateless bearer-only design. | Production origins must be exact; HTTPS, CSP, security headers, reverse-proxy controls, and deployment configuration need review. If authentication moves to cookies, revisit CSRF protection. |
| Database schema and migration risk | Flyway V1-V4 source, `ddl-auto=validate`, integer paise, constraints and indexes. | V1-V4 have not been applied to MySQL. H2 tests disable Flyway and do not verify MySQL syntax/schema/trigger behavior. DB status is BLOCKED until tested on a confirmed empty disposable schema. |
| Duplicate posting / request replay | User-scoped idempotency key and SHA-256 request fingerprint; same-key replay returns prior completed/refused result, changed request conflicts. Successful external settlement references are uniquely reserved. H2 tests cover replay and duplicate settlement reference. | MySQL concurrent key behavior and external settlement uniqueness remain unverified. Key retention/reconciliation policy is not implemented. |
| Concurrent withdrawal/transfer | Positive BIGINT paise; balances are locked by ascending account ID in one transaction; insufficient funds are recorded as FAILED without posting. H2 integration test races two withdrawals and confirms only one succeeds. | H2 does not certify MySQL isolation/locking; separately verify MySQL row locks and deadlock behavior. No load or failure-injection test on MySQL exists. |
| Database failure | Financial balances, transaction, ledger, idempotency link and audit event share a Spring DB transaction. H2 failure injection confirms rollback of all of them. | No MySQL outage/recovery, failover, backup/restore, retry, or degraded-mode test has been done. |
| Transaction rollback failure | Injected audit constraint failure in H2 leaves no transaction, balance update, ledger row or idempotency record. | Transaction manager and rollback behavior must be confirmed on MySQL; network ambiguity after commit still requires clients to retry with the same idempotency key. |
| Ledger modification / monetary integrity | Successful transfer/deposit/withdrawal creates two equal-value entries; service verifies two entries and equal totals before commit. Appends use database transaction; V1/V4 define triggers against ordinary changes; H2 tests cover posting/rollback/concurrency. | MySQL triggers/locking not run. Existing pre-V4 balances are not reconstructed as opening entries; DB administrators can alter schema/triggers. No independent accounting review/reconciliation or real-money certification exists. |
| Audit records | Admin changes and completed/refused postings append audit rows transactionally; Admin/Auditor read a bounded list. | Audit details/retention/monitoring and external tamper evidence are limited; MySQL trigger behavior remains unverified. |
| External settlement misstatement | Deposit/withdrawal routes are ADMIN-only, require a validated explicit external-settlement attestation, and store a unique reference for successful postings. LedgerLine does not connect to payment rails. | The attestation is only an application assertion; it cannot prove the external event occurred. Require independent operational controls and reconciliation; do not use this as a cash/payment integration. |

## Verification state

- Backend test/package result and frontend lint/build/test results are recorded in `DAY3_DAY7_PROGRESS.md` after the latest run. Backend tests use H2 with Flyway disabled.
- MySQL credentials were unavailable to this process. No MySQL connection, V1-V4 migration, Hibernate schema validation, MySQL health or trigger verification is claimed; no database was modified.
- Browser verification is limited to the public frontend and unauthenticated route behavior. Authenticated browser login/register and role navigation require a real backend/database; no mocked API success is claimed.

## Required before any real-fund use

First verify V1-V4 against a newly confirmed empty disposable MySQL schema, test MySQL row locks/triggers/rollback and concurrent idempotency, reconcile opening balances, complete independent accounting/security review, and establish recovery/monitoring/DB privilege controls. The present feature set is a demo ledger only. Do not interpret compilation, H2 tests, or static migration review as proof of production financial integrity.
