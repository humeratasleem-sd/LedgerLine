# LedgerLine threat model and current gaps

This register records implemented controls and remaining risks as of 2026-11-07. It is not a security certification. LedgerLine is not ready for real-money use.

| Threat | Current controls | Remaining risk / required work |
|---|---|---|
| Password attacks | Public password validation; minimum 12 characters; BCrypt; 72 UTF-8-byte limit; generic login failure; password hashes excluded from API responses. | No rate limiting, progressive delay/lockout, MFA, password reset, email verification, breached-password detection, or credential-stuffing monitoring. |
| JWT tampering / invalid tokens | HS256 signed tokens; Base64 secret must decode to at least 32 bytes; required issuer, subject, expiry, and known-role claims; expiry and signature are validated; token TTL defaults to 15 minutes. | No asymmetric key separation, rotation/key ID support, audience validation, refresh-token flow, or denylist. Symmetric key compromise enables token forgery until rotated. |
| Privilege escalation | Public registration always assigns `ACCOUNT_HOLDER`; initial ADMIN creation is an explicit, environment-gated startup bootstrap (not an HTTP endpoint); later role changes require ADMIN and are audited; roles/status are reloaded from DB per request; unknown routes fail closed. | Bootstrap secrets must be set only for first provisioning and removed afterward; secrets/host protections and operational approval processes are not managed by the app. |
| Unauthorized account access | `GET /api/accounts` is user-scoped; `GET /api/accounts/{id}` calls `AccountAuthorizationService` with the verified token subject. Tests exercise authorized and cross-user requests. | New account-scoped read/write services must call the same authorization service. Admin account creation/permission assignment must be monitored and tightly provisioned. |
| Auditor financial writes / history changes | Auditor cannot POST/PUT/PATCH/DELETE transfer or transaction routes; all ledger/audit mutations are denied; V1 append-only triggers block ordinary ledger/audit row updates/deletes. | No transaction or transfer API exists. DB administrators can alter triggers/schema; separate DB privileges, financial transaction integrity tests, external tamper evidence, and monitoring are absent. |
| Session/token misuse | Stateless API; browser token stays in JS memory (not localStorage/sessionStorage); logout clears it; 15-minute default expiry; DB status checked per request. | A live token can be read/used by injected same-origin script. Logout does not revoke a copied bearer token, which remains valid until expiry. No refresh or revocation mechanism exists. |
| Public administrator registration | Public register DTO omits role and registration forces `ACCOUNT_HOLDER`; integration test submits an `ADMIN` field and confirms the stored/returned role is `ACCOUNT_HOLDER`. Initial ADMIN provisioning is a disabled-by-default, environment-gated startup bootstrap, not a public endpoint; subsequent role changes require an ADMIN and are audited. | Operators must enable the bootstrap only for initial provisioning, protect those environment values, and disable/clear its password immediately afterward. Deployment-level approval and secret management remain external responsibilities. |
| Credential exposure | DB password and JWT secret are required environment values; `.env.example` has placeholders only; passwords are BCrypt-hashed and never returned. | Real deployment secret manager, rotation, DB privilege separation for Flyway/runtime, environment/process access controls, and log/backup protection are not configured. Do not put secrets in frontend `VITE_*` variables. |
| CORS / cross-site requests | Allowed origins are explicitly configured; credentials are not enabled; API uses bearer authorization headers rather than ambient cookies; CSRF is disabled for this stateless bearer-only design. | Production origins must be exact; HTTPS, CSP, security headers, reverse-proxy controls, and deployment configuration need review. If authentication moves to cookies, revisit CSRF protection. |
| Database schema and migration risk | Flyway V1–V3 source, `ddl-auto=validate`, integer paise, constraints and indexes; H2 integration tests exercise auth APIs. | V1–V3 have not been applied to the local MySQL instance. H2 tests disable Flyway and do not verify MySQL syntax/schema. Run migrations against MySQL 8.0.16+ before marking DB work complete. |
| Duplicate payment / request replay | V1 has a unique `(user_id, idempotency_key)` constraint and request-hash field. No payment API is exposed. | No idempotency claim/replay handler, canonical request hashing, retention, or concurrent duplicate-payment test exists. The schema alone does not prevent duplicate payments. |
| Concurrent withdrawal | V1 stores paise in `BIGINT` and checks non-negative account balance. No withdrawal endpoint exists. | No row locking/optimistic versioning or race test exists. A check constraint alone cannot prevent stale-balance races or reconcile balance with ledger. |
| Database failure | Incomplete endpoints fail closed; admin writes use database transactions, and no money movement is enabled. | No database outage/recovery, failover, backup/restore, retry, or degraded-mode test has been done. |
| Transaction rollback failure | Admin account/permission/status/role changes and their audit inserts share a Spring transaction. There is no financial transaction processor. | No injected-failure rollback test or transaction-manager/database failure test exists; financial posting rollback safety is unproven. |
| Ledger modification / monetary integrity | Ledger/audit write routes are denied; V1 append-only triggers reject ordinary ledger/audit row updates/deletes; amounts use BIGINT paise. | DB administrators can alter triggers/schema. No balanced-posting invariant, posting service, balance locking, transaction integrity/concurrency tests, or reconciliation exists. Financial integrity is not guaranteed. |
| Audit records | Admin account creation, permission changes, and user-status changes append audit events in the same DB transaction. Admin/Auditor can read a bounded, read-only event list; V1 blocks ordinary update/delete. | Transaction events are absent; no retention/monitoring, external tamper evidence, or restricted database role is implemented. |

## Verification state

- Backend `mvn test` passed: 41 tests, 0 failures/errors/skips, using an H2 test database with Flyway disabled. Tests cover authentication, role boundaries, default-disabled admin bootstrap, admin account/user/role management and audit, permission assignment/access, safe profile responses, and health.
- Backend `mvn compile`, frontend `npm run lint`, and `npm run build` passed.
- MySQL Community Server 8.0.42 was installed/running and port 3306 responded, but no application DB username/password or JWT key was configured. V1–V3 were not applied; no MySQL schema validation, MySQL-backed startup, health response, or failed-migration recovery test is claimed.
- Integrated Playwright checked the unauthenticated login/registration pages, empty-submit validation, `/accounts` redirect to `/login`, and public registration page refresh. No real registration/login, authenticated role navigation, logout, or browser 401/403 flow was testable without the backend database. A dedicated security-review agent reported no vulnerabilities in the reviewed authentication/authorization implementation.

## Required before any transfer feature

Implement and independently test transaction-bound balance updates, paired ledger postings whose totals balance, account permission enforcement, user-scoped idempotency, rollback on failure, concurrent withdrawal behavior, audit controls, and DB privilege separation. Do not interpret authentication success, compilation, H2 tests, or schema constraints as proof that financial integrity is guaranteed.
